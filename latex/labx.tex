\section{微服务系统介绍和开发}

本部分工作基于 Google Cloud 的 Online Boutique 微服务示例系统进行扩展。原系统已经具备商品浏览、购物车、结算、推荐、广告、支付、邮件、配送等典型电商功能，能够体现多语言、多服务协同工作的微服务架构特点。但是，原项目的商品购买流程并没有真正维护库存状态：用户可以反复加入商品，系统不会判断剩余库存是否足够；清空购物车也不会恢复库存；管理员也没有独立的进货入口。因此，本次开发选择围绕“库存管理”和“进货管理”补充业务能力，在原有系统上新增两个微服务，并对前端服务进行集成改造。

\subsection{原系统结构}

Online Boutique 原始系统以 \texttto{frontend} 作为用户入口，浏览器和压测程序都通过 HTTP 访问前端服务，再由前端服务调用内部微服务完成页面展示和业务处理。原系统中，\texttto{productcatalogservice} 负责商品数据，\texttto{cartservice} 负责购物车，\texttto{checkoutservice} 负责结算编排，\texttto{currencyservice}、\texttto{paymentservice}、\texttto{shippingservice}、\texttto{emailservice} 等服务分别承担货币换算、支付、配送和邮件通知等职责。整体结构如图 \ref{fig:origin_microservice_arch} 所示。

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{figure/microservice/architecture-diagram.png}
	\caption{原始 Online Boutique 微服务架构}
	\label{fig:origin_microservice_arch}
\end{figure}

从架构上看，原系统服务拆分清晰，但商品库存没有被建模为独立状态。商品目录服务只负责展示商品基本信息，购物车服务只保存用户选择的商品和数量，二者之间没有库存约束。因此，本次开发没有在页面上简单写死库存数字，而是新增独立库存服务，使库存成为可以查询、扣减、恢复和监控的业务状态。

\subsection{新增微服务设计}

本次开发新增了两个微服务：\texttto{inventoryservice} 和 \texttto{restockservice}。\texttto{inventoryservice} 是库存服务，负责维护每个商品的剩余库存、库存状态和仓库位置，并提供查询、预留、释放等能力；\texttto{restockservice} 是进货服务，作为管理员补货操作的后端入口，负责校验服务间调用凭证，并调用库存服务完成库存增加。扩展后的架构如图 \ref{fig:new_microservice_arch} 所示。

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{figure/microservice/architecture-diagram-current.png}
	\caption{新增 inventoryservice 与 restockservice 后的系统结构}
	\label{fig:new_microservice_arch}
\end{figure}

扩展后系统形成了两条主要业务链路。第一条是普通用户购物链路：用户进入商品详情页时，\texttto{frontend} 调用 \texttto{inventoryservice} 查询当前库存，并在页面上展示剩余数量；用户加入购物车时，前端先请求库存服务预留库存，成功后再写入 \texttto{cartservice}；如果购物车写入失败，前端会调用库存服务释放刚才预留的库存，避免库存凭空减少；用户清空购物车时，系统也会把购物车中已有商品数量释放回库存。第二条是管理员进货链路：管理员访问独立的 \texttto{/admin/restock} 页面，登录成功后选择商品并输入进货数量，前端携带内部 API Token 调用 \texttto{restockservice}，再由进货服务调用库存服务增加库存。

\subsection{库存服务实现概述}

\texttto{inventoryservice} 使用 Python 实现，核心职责是管理商品库存状态。服务启动时读取初始库存数据，并以商品 ID 为键保存库存数量、库存状态和仓库信息。库存状态根据剩余数量自动判断：库存为 0 时为缺货，库存较少时为低库存，其余情况为正常库存。这样前端不仅能显示“还剩多少件”，也能显示当前商品是否处于低库存或缺货状态。

库存服务提供三类核心接口。第一类是库存查询接口，用于商品详情页和管理员页面读取库存；第二类是库存预留接口，用于用户加入购物车时扣减库存；第三类是库存释放接口，用于购物车写入失败、清空购物车和管理员进货等场景。库存服务内部对库存变更操作加锁，避免并发请求同时修改同一份库存数据导致数量错误。服务还提供健康检查和 metrics 指标，便于 Kubernetes 探针和后续监控系统判断服务状态。

这种设计的关键点在于：库存判断被放在服务端，而不是只依赖前端页面限制。即使用户绕过页面直接构造请求，也必须经过库存服务校验，无法购买超过库存的数量。这样可以让库存约束成为系统后端的一部分，而不是单纯的页面展示逻辑。

\subsection{进货服务实现概述}

\texttto{restockservice} 同样使用 Python 实现，它不直接保存库存，而是承担管理员进货入口的角色。这样拆分的原因是普通用户购买商品和管理员补充库存属于不同业务角色，如果把进货逻辑混在商品详情页或购物车逻辑中，会让用户流程和管理流程混杂在一起，也不利于后续权限控制、进货记录、供应商管理等功能扩展。

进货流程采用两层保护。第一层是前端管理员登录，管理员需要使用账号密码进入 \texttto{/admin/restock} 页面；第二层是服务间 API Token，只有携带正确 Token 的前端请求才能调用进货服务。这样的设计区分了“浏览器访问权限”和“服务间调用权限”：前者保护管理员页面，后者保护进货接口本身。

当管理员提交进货数量后，\texttto{frontend} 会向 \texttto{restockservice} 发送请求；进货服务校验 Token 和参数后，再调用 \texttto{inventoryservice} 更新库存。操作成功后，页面显示进货成功弹窗，管理员点击确认后刷新页面，从而看到更新后的库存数量。相关界面和操作效果截图放在附录 \ref{sec:appendix_microservice_figures} 中。

\subsection{前端集成改造}

原 \texttto{frontend} 服务使用 Go 实现，是用户访问系统的统一入口。本次开发在前端中增加了库存查询、库存预留、库存释放和管理员进货页面的调用逻辑。普通用户打开商品详情页时，页面会展示该商品的剩余库存、库存状态和仓库位置；商品数量选择框会根据库存动态限制最大可选数量，避免页面上直接选择超过库存的数量。

加入购物车时，前端不再直接写入购物车，而是先向库存服务申请预留库存。只有库存预留成功后，才继续调用购物车服务。如果购物车服务写入失败，前端会立即释放库存，完成一次简单的补偿操作。清空购物车时，前端先读取购物车内容，再调用购物车服务清空，最后把购物车中原有商品数量逐项释放回库存。通过这些改造，系统实现了“加入购物车扣减库存、清空购物车恢复库存、库存不足拒绝加入”的基本闭环。

管理员页面则被设计为独立模块，而不是放在普通商品购买流程中。管理员访问 \texttto{/admin/restock} 后先看到登录页面，登录成功后进入进货页面。页面列出商品、当前库存和进货输入框，管理员提交后由前端调用进货服务。这样既保持了普通用户页面的简洁，也让管理操作有清晰的入口和权限边界。

\subsection{部署与测试}

两个新增服务都补充了 Dockerfile、Kubernetes Deployment 和 Service 配置，并加入到 skaffold 构建流程中。\texttto{frontend} 通过环境变量读取库存服务和进货服务地址，例如 \texttto{INVENTORY\_SERVICE\_URL} 和 \texttto{RESTOCK\_SERVICE\_URL}。在 Kubernetes 中，服务之间不使用 \texttto{localhost} 通信，而是通过 Service 名称进行访问，例如 \texttto{inventoryservice} 和 \texttto{restockservice}。这样可以适应 Pod 动态创建和销毁的环境。

测试方面，库存服务重点验证库存查询、库存预留、库存不足拒绝、库存释放和异常商品 ID 等场景；进货服务重点验证 Token 校验、参数校验、进货成功和依赖库存服务失败等场景。前端功能则通过手动操作验证：商品详情页能看到库存，加入购物车后库存减少，清空购物车后库存回滚，管理员登录后可以进货，进货成功后弹窗提示并刷新页面。测试截图和 Kubernetes 运行状态截图统一放在附录中。


\section{部署、故障注入与监控、数据采集分析}
本部分围绕 Online Boutique 微服务系统完成部署、监控体系搭建、故障注入和指标数据采集。实验流程从 Kubernetes 集群中运行微服务开始，随后部署 Prometheus、Grafana、Fluentd 和 Chaos Mesh，在可控故障窗口中采集节点与系统指标，最终为后续 FluxEV 时间序列异常检测复现提供 OPS 数据集。

\subsection{部署}

本部分部署对象为基于 Google Online Boutique 扩展的微服务系统。项目在原有在线精品店业务基础上增加了库存管理和管理员进货相关功能，同时保留前端、购物车、商品目录、支付、结算、推荐、邮件、配送、广告、货币转换、Redis 购物车和负载生成器等典型微服务组件。系统部署文件位于 \texttto{ops/kubernetes-manifests.yaml}，使用 Kubernetes Deployment、Service 与 ServiceAccount 描述各服务实例和访问关系。

\subsubsection{集群启动}

实验环境使用 minikube 构建本地 Kubernetes 集群。考虑到微服务数量较多，同时还需要运行 Prometheus、Grafana、日志采集与 Chaos Mesh，启动集群时分配了 12 个 CPU 和约 7.6 GB 内存，并配置镜像加速地址以提高国内网络环境下的镜像拉取成功率。启动命令如下：

\begin{lstlisting}[language=bash]
minikube start \
    --driver=docker \
    --cpus=12 \
    --memory=7605MB \
    --image-mirror-country=cn \
    --registry-mirror=https://docker.njdldkl666699.dpdns.org \
    --registry-mirror=https://k8s.njdldkl666699.dpdns.org \
    --registry-mirror=https://quay.njdldkl666699.dpdns.org
\end{lstlisting}

\subsubsection{微服务部署}

集群启动后，首先进入 \texttto{ops/} 目录并应用微服务清单：

\begin{lstlisting}[language=bash]

该清单会创建 Online Boutique 相关服务和外部访问入口。集群中 Pod 的运行状态见附录图~\ref{fig:appendix_ops_cluster_pods}。其中 \texttto{frontend-external} 用于在 minikube 环境中暴露前端页面，可通过如下命令创建隧道并访问，访问效果见附录图~\ref{fig:appendix_ops_frontend_page}。

\begin{lstlisting}[language=bash]

\end{lstlisting}

\subsubsection{监控部署}

监控部分采用 Prometheus + Grafana。Prometheus 负责采集 Kubernetes 集群和节点指标，Grafana 负责可视化展示。部署时使用 \texttto{kube-prometheus-stack} Helm Chart，并创建独立的 \texttto{monitoring} 命名空间：

\begin{lstlisting}[language=bash]
helm repo add prometheus-community "https://helm-charts.itboon.top/prometheus-community"
helm repo update
helm install prometheus prometheus-community/kube-prometheus-stack --namespace monitoring --create-namespace
\end{lstlisting}

Grafana 默认管理员密码以 Secret 形式保存在集群中，可通过如下命令解码：

\begin{lstlisting}
$secret = kubectl get secret prometheus-grafana -n monitoring -o jsonpath="{.data.admin-password}"
$password = [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($secret))
Write-Host "Grafana admin password: $password"
\end{lstlisting}

\section{FluxEV 论文复现}

\subsection{论文介绍}

FluxEV 全称为 ``FluxEV: A Fast and Effective Unsupervised Framework for Time-Series Anomaly Detection''，发表于 WSDM 2021\cite{li2021fluxev}。论文面向在线服务监控中的时间序列异常检测问题，强调两个现实约束：一是实际运维指标数量大、标签少，难以依赖监督学习；二是检测需要流式、快速、可持续更新，复杂模型的训练和推理成本不适合大规模监控场景。

论文的出发点是 SPOT 虽然能够基于极值理论进行自动阈值检测，但直接应用在原始数值上时，只对全局分布中的极端值敏感。很多真实异常并不是绝对数值最大或最小，而是“不符合局部和周期规律的波动”。例如，一个业务指标在高峰期大幅波动可能是正常现象，而在低峰期出现同样幅度的波动反而可能是异常。因此，FluxEV 的核心思想是：先把时间序列中的异常波动转化为更容易被 SPOT 捕捉的极端特征，再用自动阈值完成无监督检测。

\subsubsection{算法流程}

FluxEV 框架主要包含四个步骤：

\begin{enumerate}
	\item 数据预处理。对时间戳缺失、缺失值和不同采样间隔进行处理，保证输入序列可以按固定时间间隔流式计算。
	\item 波动提取。使用 EWMA 预测当前点的期望值，将当前值与预测值之间的误差作为局部波动。
	\item 两步平滑。第一步顺序平滑用于削弱局部噪声，保留会显著改变窗口标准差的波动；第二步周期平滑用于比较相邻周期中相同时间槽附近的历史波动，从而消除正常周期模式的影响。
	\item 自动阈值。对平滑后的波动特征应用 SPOT/POT，通过广义帕累托分布拟合尾部分布，并使用矩估计 MOM 替代 MLE 以提升参数估计效率。
\end{enumerate}

图~\ref{fig:fluxev_algorithm_flow} 展示了 FluxEV 从原始序列到异常判断的整体流程。

\begin{figure}[H]
	\centering
	\includegraphics[width=0.7\textwidth]{figure/fluxev/algorithm-flow.png}
	\caption{FluxEV 算法流程}
	\label{fig:fluxev_algorithm_flow}
\end{figure}

在输入输出形式上，FluxEV 的输入是一条或多条按时间排序的单变量时间序列，通常包含 \texttto{timestamp}、\texttto{value} 和可选 \texttto{label}。算法训练阶段只需要一段初始化数据来校准 SPOT 阈值，不依赖标签。输出是与测试时间点对应的 0/1 异常判断，其中 1 表示异常点。复现实验中，若数据集带有标签，则使用 F1、Recall、Precision 评价检测效果。具体算法步骤如图~\ref{fig:fluxev_algorithm_steps} 所示。

\subsubsection{重构实现}

本仓库中的重构实现位于 \texttto{FluxEV/fluxev/}。其中 \texttto{detector.py} 实现 EWMA、两步平滑与流式检测逻辑；\texttto{spot.py} 实现 SPOT、GPD 参数估计和 MOM/MLE 两种估计方式；\texttto{datasets.py} 封装 KPI、Yahoo 和 OPS 三类数据集运行流程；\texttto{preprocessing.py} 与 \texttto{ops\_preprocessing.py} 分别处理公开 KPI 数据和自采集 OPS 数据。

\subsection{数据预处理}

本次复现使用三类数据：AIOps/KPI 数据集、Yahoo S5 benchmark 数据集，以及本项目自采集的 OPS 数据集。三类数据的来源和预处理方式不同，但最终都被整理为 FluxEV 可接受的单变量时间序列检测任务。

\subsubsection{KPI 数据集}

AIOps/KPI 数据集来自 AIOps Challenge，原始文件放置在：

\begin{lstlisting}
FluxEV/data/AIOps/phase2_train.csv
FluxEV/data/AIOps/phase2_ground_truth.hdf
\end{lstlisting}

KPI 数据包含多条脱敏 KPI 曲线，每条曲线有时间戳、值、标签和 KPI ID。由于原始数据存在缺失点，预处理首先按最小时间间隔补全时间戳，并使用 \texttto{missing} 列标记补出的点；随后将训练集和测试集合并为 \texttto{total\_data.csv}，并用 \texttto{is\_test} 标识样本来源。缺失值填充支持线性插值和周期填充，本次默认使用周期填充，以尽量保留日周期或业务周期模式。运行命令如下：

\begin{lstlisting}[language=bash]
cd FluxEV
uv run -m fluxev.cli preprocess-kpi
\end{lstlisting}

\subsubsection{Yahoo 数据集}

Yahoo 数据集使用 Webscope S5 benchmark，包含 A1、A2、A3、A4 四组序列。其中 A1 是真实生产流量数据，A2、A3、A4 是人工合成或带有不同周期模式的序列。仓库中数据按如下结构组织：

\begin{lstlisting}
FluxEV/data/Yahoo/A1Benchmark/*.csv
FluxEV/data/Yahoo/A2Benchmark/*.csv
FluxEV/data/Yahoo/A3Benchmark/*.csv
FluxEV/data/Yahoo/A4Benchmark/*.csv
\end{lstlisting}

Yahoo 各组字段名略有差异。实现中通过 \texttto{read\_yahoo\_data} 统一字段，将 \texttto{timestamp}/\texttto{timestamps}、\texttto{value}、\texttto{is\_anomaly}/\texttto{anomaly} 规范化为 \texttto{timestamp}、\texttto{value}、\texttto{label}。检测时默认使用序列前半段作为初始化数据；A2 组使用一阶平滑，其他组使用二阶平滑，周期参数按论文复现设置处理。

\subsubsection{OPS 数据集}

OPS 数据集来自本项目的运维实验。原始数据为 Grafana 导出的多指标 CSV，目录为 \texttto{ops/metrics/}，原始 CSV 示例见附录图~\ref{fig:appendix_fluxev_original_csv}。由于 Grafana 导出的 CSV 通常是一个文件包含多条指标曲线，不能直接作为 FluxEV 输入，因此 \texttto{ops\_preprocessing.py} 将其拆分为单指标序列，并写入：

\begin{lstlisting}
FluxEV/data/OPS/
\end{lstlisting}

OPS 预处理主要包括以下步骤：

\begin{enumerate}
	\item 按指标类型选择波动较明显、与故障相关的 CSV 文件，例如 CPU、Memory、Network Traffic、Network Saturation、Disk IO、PSI、System Processes、TCP Errors 等。
	\item 解析 Grafana 中带单位的数值，例如 \%、\texttto{KB/s}、\texttto{MB}、\texttto{ms}、\texttto{ops/s} 等，并转换为统一的浮点数。
	\item 将多指标 CSV 拆成单指标 CSV，输出字段包括 \texttto{timestamp}、\texttto{value}、\texttto{label} 和 \texttto{window\_label}。
	\item 根据 Chaos Mesh 实验时间窗口生成粗粒度窗口标注 \texttto{window\_label}。
	\item 用故障窗口外的数据计算正常基线 p01/p99，仅在对应实验窗口内将超出正常范围的点标为异常，生成 FluxEV 默认使用的点级 \texttto{label}。
	\item 过滤人工确认几乎没有变化的 veth 网络指标，以及部分点级正样本为 0 的无效 Rx 指标。
\end{enumerate}

预处理命令如下：

\begin{lstlisting}[language=bash]
cd FluxEV
uv run -m fluxev.cli preprocess-ops
\end{lstlisting}

预处理后生成 \texttto{manifest.csv}，记录每条输出指标对应的源文件、指标名、关联故障窗口、行数、点级异常数、窗口异常数和 p01/p99 基线，示例见附录图~\ref{fig:appendix_fluxev_ops_manifest}。当前 OPS 数据集共保留 77 条指标，其中 \texttto{CPU\_Memory\_Net\_Disk} 60 条，\texttto{System\_Processes} 13 条，\texttto{Network\_Netstat} 3 条，\texttto{Network\_Sockstat} 1 条。每条序列约 690 个采样点，能够覆盖两次 30 分钟故障实验及其前后状态。

论文中 FluxEV-MOM 在 KPI 上的 F1 约为 0.790，在 Yahoo 上的 F1 约为 0.666。与论文结果相比，本次 KPI 复现 F1 为 0.7970，基本达到并略高于论文报告值；Yahoo 复现 F1 为 0.6397，低于论文报告值约 0.026。造成 Yahoo 差异的原因可能包括数据版本、文件划分、周期参数细节、延迟容忍范围和实现差异。整体来看，复现结果仍然符合论文结论：FluxEV 在不依赖监督标签训练的条件下，可以获得较高的异常检测精度。

OPS 数据集没有论文中的基准结果，因此主要用于验证 FluxEV 在本项目真实运维指标上的适用性。OPS 总体 F1 为 0.7849，Precision 达到 0.8765，说明模型在自采集指标上误报相对较少；Recall 为 0.7106，说明仍存在部分故障窗口内的异常波动未被捕捉。逐指标结果中，77 条指标全部完成评估，其中 63 条正常完成 SPOT 检测，14 条因初始化峰值不足等原因使用零预测兜底。效果最好的指标集中在 CPU saturation、CPU pressure、磁盘读吞吐、CPU user/system/softirq 等与 stress-test 强相关的序列，部分 F1 达到 0.98--1.00，逐指标结果示例见附录图~\ref{fig:appendix_fluxev_ops_individual_results}。

OPS 结果也体现了自采集运维数据的特点。资源压力故障往往造成 CPU 与磁盘类指标出现稳定且持续的异常波动，因此 FluxEV 容易通过局部波动和阈值检测捕获；网络丢包故障的影响更依赖具体服务链路和流量方向，部分网络接口指标变化不明显，或者异常表现不是单点尖峰，而是吞吐下降、连接重试和服务延迟的组合，因此单变量 FluxEV 的召回率相对受限。后续若继续改进，可以将 OPS 数据扩展到服务级延迟、请求错误率、gRPC 状态码和应用日志异常，并结合多指标关联分析补充单变量检测的不足。

综上，本部分完成了从微服务部署、故障注入、监控采集到异常检测复现的闭环。部署与监控部分提供了真实的运维实验环境；Chaos Mesh 提供了可控的异常窗口；OPS 预处理将 Grafana 指标转化为可复现实验数据；FluxEV 复现则验证了基于波动特征与极值理论的无监督时间序列异常检测方法在公开数据集和自采集微服务指标上的效果。

\subsection{LightLog复现}

\subsubsection*{论文介绍}
LightLog\cite{wang2022lightlog} 论文提出了一种面向边缘设备的轻量级日志异常检测方法，旨在解决现有深度学习方法（如 DeepLog、LogAnomaly）计算量大、难以在资源受限的边缘设备上实时部署的问题。该方法从两个维度实现轻量化：首先，在数据预处理阶段，采用 Word2Vec 将日志模板转换为 300 维语义向量，再通过 PCA-PPA（Post-Processing Algorithm）降维至 20 维，在保留语义信息的同时大幅减少存储和计算开销；其次，设计了一种增强型时序卷积网络（TCN），通过因果卷积保证时序正确性，通过扩张卷积（d=1,2,4,8）在不增加参数的前提下扩大感受野，并在残差块中引入多核卷积（kernel=2,3,4）和 Pointwise 卷积来提升精度并压缩参数。

\subsubsection{论文主要框架}
LightLog\cite{wang2022lightlog} 从非结构化日志到异常检测的完整流程包含四个核心步骤：

\paragraph{步骤1：日志解析}
使用 FT-Tree 将非结构化日志解析为结构化模板。
\begin{center}
\verb|"Interface ae1 changed state to up at 2024-01-01 10:00:00"| \\
$\downarrow$ \\
\verb|"Interface <*> changed state to up at <TIME>"|
\end{center}

\paragraph{步骤2：Word2Vec 向量化}
将日志模板转换为 300 维语义向量，捕捉模板间的语义关系。

\paragraph{步骤3：PCA-PPA 降维}
将 300 维语义向量降维至 20 维，适配边缘设备。论文中原始 300 维向量需要 0.46M 内存，降维后能大幅压缩，实现降维不降精度。
\begin{center}
300维 $\rightarrow$ 20维
\end{center}

\paragraph{步骤4：优化后的 TCN（核心）}
针对时序日志预测，设计了四项优化（下面进行详细介绍）：
\begin{itemize}
\item 因果卷积（Causal Convolution）
\item 扩张卷积（Dilated Convolution）
\item 增强残差块（Enhanced Residual Block）
\item 全局平均池化（Global Average Pooling, GAP）
\end{itemize}

\subsubsection{优化后的 TCN：四大核心改进}

LightLog 在传统 TCN 基础上引入了四项关键优化，在保证高检测精度的同时大幅降低了模型参数量和计算复杂度，使其能够高效部署于资源受限的边缘设备。

\begin{enumerate}
\item \textbf{因果卷积（Causal Convolution）}
    
因果卷积是 TCN 的基础组件，其核心思想是保证模型在预测当前时刻的输出时，只能依赖于当前及之前时刻的输入信息，而不能“看到”未来的数据。这一特性对于时序建模至关重要，避免了未来信息泄露导致的不合理预测。
\begin{itemize}
\item 传统卷积：[L1, L2, L3, L4, L5] $\rightarrow$ 预测 L3 看到 L4, L5，这在时序任务中是不合理的。
\item 因果卷积：[L1, L2, L3] $\rightarrow$ 预测 L4 只看 L1-L3，保证了时序预测的合理性。
\end{itemize}

\item \textbf{扩张卷积（Dilated Convolution）}
    
扩张卷积通过在卷积核元素之间插入空洞（即跳过部分输入）来扩大感受野，使得模型能够捕捉更长距离的时序依赖关系，同时不增加额外的参数量。LightLog 中设置扩张率 $d = 1, 2, 4, 8$，卷积核大小 $k = 3$。
\begin{itemize}
\item $d=1$：感受野为 3，对应相邻的 3 个日志 [L1, L2, L3]；
\item $d=2$：感受野为 6，采样位置为 [L1, L3, L5]（每隔 2 个取一个）；
\item $d=4$：感受野为 12，采样位置为 [L1, L5, L9]（每隔 4 个取一个）。
\end{itemize}
通过堆叠不同扩张率的卷积层，TCN 能够在参数不增加的情况下获得指数级扩大的感受野，有效捕捉日志序列中的长程模式。

\item \textbf{增强残差块（Enhanced Residual Block）}
    
残差结构通过跳跃连接（skip connection）将输入直接加到输出上，有效缓解了深层网络训练中的梯度消失问题。LightLog 在此基础上对残差块进行了两项增强：
\begin{itemize}
\item \textit{多核卷积}：在残差块内并行使用多个不同尺寸的卷积核（kernel size = 2, 3, 4），从不同尺度提取日志序列的特征模式，丰富低层特征表示，显著提升检测精度；
\item \textit{Pointwise 卷积}：采用 $1 \times 1$ 卷积对多核输出的特征通道进行融合，在保持特征表达能力的同时大幅减少参数量，实现模型轻量化。
\end{itemize}

\item \textbf{全局平均池化（Global Average Pooling, GAP）}
    
传统 CNN 通常在末端使用 Flatten 操作将特征图展平后接入全连接层进行分类，这会导致参数量急剧增加。LightLog 采用全局平均池化替代 Flatten，对每个特征通道的所有时间步取平均值，将输出维度从 $T \times C$ 压缩至 $C$，大幅减少了后续全连接层的参数量，同时有效降低了过拟合风险，提升了模型的泛化能力。
\end{enumerate}

\subsection{LogAnomaly与LogRobust的复现及对比实验}

\subsubsection{LogAnomaly复现}
我们阅读了LogAnomaly\cite{meng2019loganomaly}并对其进行了复现,下面介绍LogAnomaly论文的基本原理

LogAnomaly 是一个基于深度学习的日志异常检测框架，其核心思想是将日志流建模为自然语言序列，通过提取日志模板的语义信息来实现异常检测。整个处理流程主要包含以下四个步骤：

\textbf{1.日志解析：} 首先采用 FT-Tree 算法将非结构化的原始日志解析为结构化的日志模板，例如将 "Interface ae1 changed state to up at 2024-01-01 10:00:00" 解析为 "Interface <*> changed state to up at <TIME>"。这是后续语义分析的基础。

\begin{figure}[H]
	\centering
	\includegraphics[width=0.90\textwidth]{figure/LightLog/LightLog/Examples of template2Vec.jpg}
	\caption{template2Vec方法示例}
	\label{fig:ops_stress_test}
\end{figure}
\textbf{2.模板向量化：} 提出 template2Vec 方法，基于同义词和反义词集合，利用 dLCE 词嵌入模型为每个模板生成语义向量，从而将日志流转化为向量序列。相比仅使用模板索引的传统方法，该方式能够有效捕捉模板之间的语义关联，减少因模板表面差异导致的误报。

\textbf{3.双模式学习：} 使用两层 LSTM 网络同时学习日志的两种模式：
\begin{itemize}
\item \textit{顺序模式（Sequential Pattern）}：学习模板向量的时序依赖关系，预测下一个可能出现的模板；
\item \textit{定量模式（Quantitative Pattern）}：学习滑动窗口内各类模板的计数不变关系，如文件中 "打开" 与 "关闭" 操作的数量应保持平衡。
\end{itemize}

\textbf{4.在线检测：} 系统将实时日志匹配到已有模板，若遇到新模板则通过计算其临时模板向量与已有模板向量的相似度进行近似匹配。基于训练好的 LSTM 模型，结合顺序与定量两种模式的预测结果，综合判定日志序列是否异常。

LogAnomaly 通过引入语义信息并同时检测两类异常，有效解决了传统方法中仅依赖模板索引带来的误报问题。

\section{运维智能体}
\subsection{问题背景}
随着微服务架构在生产环境中的广泛落地，
单个业务系统往往被拆分为数十甚至上百个 Kubernetes 资源对象（Deployment、StatefulSet、Service、Pod、ConfigMap 等），
并通过容器编排平台进行动态调度。
这一架构在提升可扩展性的同时，也给运维带来了新的挑战：
\begin{itemize}
	\item 集群状态复杂：运维人员需要实时监控大量 Pod、Node、Deployment 等资源的状态，手动巡检效率低下。
	\item 异常检测困难：系统异常表现形式多样，仅凭经验难以快速识别和分类。
	\item 根因分析耗时：出现故障时需要关联日志、指标、事件等多维度数据进行分析，且响应链路往往比较长，导致分析耗时较长。
	\item 强依赖经验：故障定位与恢复建议高度依赖运维工程师的个人经验，难以标准化与传承。
\end{itemize}
\par
为解决上述问题，本项目设计并实现了一套基于大语言模型（LLM）的微服务运维智能体（Ops Agent），
其目标是构建一个能自动感知集群状态、自动分析异常根因、自动生成恢复方案的智能系统，
闭环完成"检测—定位—恢复"这一运维核心链路。
智能体既可作为独立 CLI 工具被运维工程师直接调用，
也可通过 Web 前端以图形化界面形式使用，
对 Kubernetes 集群进行定时轮询监控与异常分析，
实现自动化的智能运维。

\subsection{实现的功能}
本系统在加分项给出的四项可选能力中实现了三项功能：异常检测、根因分类、故障恢复建议。
智能体会定时自动收集 Kubernetes 集群中 Pod、Node、Deployment、Service 等资源的状态信息，
并基于规则引擎进行快速的异常检测，
识别出异常的资源或事件，并给异常划分严重等级；
发现异常后，智能体会自动调用大语言模型对检测到的异常进行智能根因分析，
并对分析结果提供置信度评分，帮助用户判断分析可靠性；
最后，智能体还会根据分析结果生成故障恢复建议，
并为每个恢复步骤标注风险等级，提醒用户注意操作风险，
同时为每个恢复步骤附带验证命令或方法，方便用户确认操作效果是否生效。
\par
另外，本系统还实现了集群性能分析的功能：
智能体支持集成 Prometheus，可以采集 CPU、内存、网络等性能指标，
并利用大语言模型对指标数据进行分析，
标明集群的各项负载，
指出是否存在性能瓶颈，帮助用户更好地分配系统资源；
智能体还会根据业务活动数据，总结业务增长及分布特征，
帮助用户更好地把握业务趋势；
同时，智能体也会针对性能与业务数据，给出集群优化建议，
指导用户优化集群性能。
\par
同时，系统也保留了直接与智能体对话的功能，用户可以直接通过自然语言与智能体进行交互，
使用智能体查询集群状态、分析异常、获取日志等，而不必受限于预设工作流的提示词模板，
这为用户提供了更大的灵活性和便利性。
系统整体采用模块化的设计，提供统一接口，
未来可以方便地扩展更多Agent工具和工作流，
以满足不同场景下的运维需求。

\subsection{关键技术细节}
\subsubsection{工具调用机制（Tool Calling）}
工具调用是 Agent 智能体区别于传统聊天机器人的关键。
本项目采用标准的 OpenAI Function Calling 协议实现工具调用：
\begin{enumerate}
	\item 工具注册：每个工具继承 BaseTool 基类，定义 name、description 和 parameters 属性。
	\item 工具描述生成：ToolRegistry 将工具信息转换为 OpenAI 格式的 Function Schema。
	\item LLM 调用：将工具列表传递给 LLM，LLM 根据用户需求决定是否调用工具。
	\item 工具执行：解析 LLM 返回的 tool\_calls，调用对应的工具并获取结果。
	\item 结果反馈：将工具执行结果作为新消息加入上下文，继续 LLM 对话循环。
\end{enumerate}
新增工具只需继承 BaseTool 并在 register\_xxx\_tools$\left( \right)$ 中注册，即可被智能体自动调用，
实现了插件化扩展。
\par
在本项目中，为满足运维的需要，智能体实现了三大类工具，具体如下：
\begin{itemize}
	\item K8s 监控工具（8个）：
	\begin{enumerate}
		\item get\_cluster\_status：获取集群整体状态。
		\item list\_pods：列出 Pod，支持标签筛选。
		\item get\_pod\_detail：获取 Pod 详细状态、事件、条件。
		\item get\_pod\_logs：拉取 Pod 日志。
		\item list\_deployments：列出 Deployment 及副本数。
		\item list\_services：列出 Service。
		\item list\_nodes：列出所有 Node。
		\item list\_events：列出 Warning 事件。
	\end{enumerate}
	\item Prometheus 监控工具（5个）：
	\begin{enumerate}
		\item prometheus\_query：自定义 PromQL 即时/范围查询。
		\item cluster\_metrics：获取集群整体 CPU/内存指标。
		\item server\_metrics：获取服务器 CPU/内存/网络趋势指标。
		\item node\_metrics：获取各节点资源使用情况。
		\item metrics\_comparison：对比两个时段指标数据。
	\end{enumerate}
	\item 日志分析工具（2个）：
	\begin{enumerate}
		\item k8s\_get\_pod\_logs：通过 K8s API 获取 Pod 日志。
		\item es\_query\_logs：通过 ElasticSearch 查询日志。
	\end{enumerate}
\end{itemize}

\subsubsection{大模型提示词工程（LLM Prompt）}
智能体的系统提示（SYSTEM\_PROMPT）明确约束了输出格式（严格 JSON），并通过三类任务级 prompt 分阶段调用：
\begin{enumerate}
	\item 异常检测 prompt：输入 K8s 状态 + Prometheus 指标 + 事件，输出异常列表。
	\item 根因分析 prompt：输入异常 + 日志 + 指标趋势，输出根因分类。
	\item 恢复建议 prompt：输入根因 + 当前状态，输出有序恢复步骤。
\end{enumerate}
每个 prompt 都附带"注意事项"段（如"category 必须从指定列表中选择"），
降低 LLM 输出格式漂移的概率。
LLM 失败时通过 \_parse\_json\_response$\left( \right)$ 中的正则提取 $\left\{...\right\}$ 块进行兜底，
再失败则使用基于分类的默认模板，保证系统可用性。

\subsubsection{异步任务管理}
AnomalyAnalyzer 在独立线程中执行 LLM 分析，主线程的轮询任务无需等待 LLM 返回；
使用不同的 ID 来对 LLM 分析任务进行会话隔离，确保分析任务相互独立；
AnalysisTaskManager 维护任务队列与状态机（pending / running / completed / failed），
前端可通过 /anomaly/status 实时查询分析进度；
同时，使用锁机制确保同一时间只有一个分析任务在执行，避免并发问题。
这样使得后台的 LLM 分析任务可以并行执行，
大大提高了分析速度，优化了用户体验。

\subsection{遇到的问题及解决方案}
\subsubsection{Prometheus 客户端重试机制}
Windows 环境下 Prometheus HTTP 连接常出现 WinError 10054（远程主机强迫关闭）的错误。
经过研究，最终通过以下策略解决了该问题：
\begin{itemize}
	\item 指数退避：每次重试间隔 delay * （attempt+1）。
	\item 可重试异常过滤：仅对 connection / timeout / reset 类错误重试。
	\item 重试前回调：\_before\_retry 重置 HTTP 客户端（关闭旧连接、创建新连接），绕过被服务器主动关闭的 keep-alive 连接。
\end{itemize}

\subsubsection{最大调用次数限制}
LLM 有时会陷入无限工具调用的循环。
为防止 LLM 无限调用工具，项目引入了最大调用次数限制（可在 .env 中配置，默认值为 10 次）。
在 LLM 调用工具时，会检查当前调用次数是否超过限制，
如果超过则返回错误信息。

\section{总结与展望}
\subsection{项目总结}
本项目围绕微服务运维全链路，完成了从系统开发、部署监控、故障注入、数据采集到异常检测算法复现与智能运维体搭建的完整闭环实验，主要成果如下：

\textbf{微服务系统开发方面}，在 Online Boutique 原有系统基础上新增了库存服务和进货服务，并完成了前端集成、容器化部署和功能测试。库存服务让商品库存从静态页面信息变成独立业务状态，支持查询、扣减、释放和监控；进货服务将管理员补货从普通购买流程中拆分出来，并通过管理员登录和 API Token 进行保护。经过改造后，系统形成了较完整的库存业务闭环：用户购买会占用库存，取消购物车会恢复库存，库存不足会拒绝请求，管理员可以在独立页面补充库存。该过程体现了微服务系统中服务拆分、接口协作、状态一致性、服务发现和可测试性的基本思想。

\textbf{运维实验平台搭建方面}，基于 Dockerfile镜像构建+Kubernetes容器编排 完成了完整微服务集群部署，通过 Prometheus + Grafana 构建监控体系，利用 Fluentd 实现日志采集，借助 Chaos Mesh 注入网络丢包和资源压力两类可控故障。在约 6 小时的监控窗口内，采集了涵盖 CPU、内存、网络、磁盘、系统负载等多维度的 OPS 运维指标数据集，为后续异常检测实验提供了真实数据基础。

\textbf{指标异常检测复现方面}，对 FluxEV 论文进行了完整复现。AIOps/KPI 数据集上达到 F1=0.7970（略高于论文报告的 0.790），Yahoo 数据集上达到 F1=0.6397（与论文 0.666 存在约 0.026 差距，可能与数据版本及参数细节有关）。OPS 自采集数据集总体 F1=0.7849，Precision=0.8765，表明模型在自采集指标上误报较少，验证了 FluxEV 在真实运维场景中的适用性。

\textbf{日志异常检测方面}，构建了基于 Fluentd 采集 + Chaos Mesh 故障注入的自建日志数据集，共约 23 万条序列。完整复现了 LightLog、LogAnomaly 和 LogRobust 三种方法，并开展了消融实验与对比实验。LightLog 在自建数据集上达到 F1=0.9835，参数量仅 8,050（约为 LogAnomaly 的 3.2\%、LogRobust 的 1.4\%），测试速度相比 LogRobust 提升约 23 倍，验证了轻量化时序卷积网络在日志异常检测中的有效性与高效性。

\textbf{运维智能体开发方面}，设计并实现了基于大语言模型的 Kubernetes 运维智能体系统，实现了三项核心能力：异常检测、根因分类与故障恢复建议。系统以模块化工具调用机制为基础，集成了 Kubernetes 监控、Prometheus 指标查询和日志分析三类共 15 个工具，通过前端界面提供集群概览、智能对话、性能分析和历史记录等功能。实际测试表明，智能体能够准确定位异常根因（如网络问题导致镜像拉取失败）并给出可操作的恢复建议，验证了 LLM 在运维场景中的应用价值。

\textbf{测试方面}，采用 Selenium IDE 完成了系统功能自动化测试，打通了从商品浏览到下单的全业务流程；使用 JMeter 开展了多维度压力测试与边界值安全测试，覆盖了 HTTP/gRPC 接口压测、依赖链路测试和注入攻击测试，验证了系统在并发压力和安全攻击下的鲁棒性。

\subsection{对未来的展望}
基于本项目的成果与经验，未来可以从以下方向继续推进：

\textbf{算法层面}，可探索多变量时间序列异常检测方法（如基于图神经网络或 Transformer 的多指标联合建模），进一步提升对复杂故障模式的识别能力。同时，可引入持续学习机制，使检测模型能够适应业务指标的周期性变化，降低误报率。

\textbf{日志分析层面}，可扩展日志模板的语义表示能力，探索大语言模型在少样本日志解析与异常检测中的应用，减少对大规模标注数据的依赖。

\textbf{智能体层面}，可构建运维知识图谱或本地 RAG 知识库，提升智能体的推理深度和回答准确性；引入工具安全审计与用户授权机制，逐步实现“检测→定位→修复”的完整自动化闭环；支持多集群管理和历史趋势分析，增强智能体的实用性和覆盖范围。

\textbf{实验验证层面}，未来可在更大规模集群上开展实验，验证算法与系统在真实生产环境中的可扩展性，并探索 ChaosMesh 与智能体的联动，实现“故障注入→智能体检测→自动恢复”的端到端验证。

总体而言，本项目为微服务运维的自动化、智能化探索提供了较为完整的实验平台与方法积累，后续可在此基础上有针对性地进行深入研究和工程化落地。
