\section{微服务系统介绍和开发}

\subsection*{实验目的与开发背景}

本部分实验的目标是在已有的 Online Boutique 微服务系统基础上，完成一个相对完整的业务扩展：为原本只具备商品浏览、购物车和模拟下单能力的电商系统增加库存管理能力，并进一步将进货操作从普通用户购买流程中拆分出来，设计为一个独立的管理员模块。通过这一开发过程，可以更加直观地理解微服务系统中“服务拆分、接口协作、状态一致性、容器化部署、服务发现、健康检查与监控指标”之间的关系。

Online Boutique 是 Google Cloud Platform 提供的经典微服务示例项目，原始系统由多个不同语言实现的服务组成，例如 Go 编写的 frontend、productcatalogservice、checkoutservice 和 shippingservice，C\# 编写的 cartservice，Python 编写的 emailservice 与 recommendationservice，Node.js 编写的 currencyservice 和 paymentservice，以及 Java 编写的 adservice。该系统适合作为课程大作业基础，一方面是因为它本身已经具备真实微服务系统的基本形态，另一方面是因为它的业务流程清晰，便于围绕电商场景进行扩展。

原系统的主要业务链路是：用户访问前端页面，浏览商品目录，查看商品详情，将商品加入购物车，最后完成模拟结算。该过程能够体现微服务之间通过网络调用协作完成业务功能的特点，但是原项目并没有真正维护商品库存。也就是说，商品能否购买、库存是否足够、购物车清空后库存是否回滚、管理员是否能够补货等问题，在原系统中并没有被建模。因此，本实验选择“库存管理”和“进货管理”作为新增微服务开发内容。

本次开发最终新增了两个微服务：

\begin{itemize}
	\item \textbf{inventoryservice：库存服务。} 该服务负责保存商品库存状态，提供库存查询、库存预留、库存释放、健康检查和监控指标等接口。
	\item \textbf{restockservice：进货服务。} 该服务作为独立的管理员进货模块后端，负责接收前端管理员页面提交的进货请求，校验内部 API Token，并调用库存服务完成库存增加。
\end{itemize}

同时，原有 Go 前端也进行了配套改造：商品详情页可以显示库存数量和仓库信息，购买数量会受到库存上限限制，加入购物车时会扣减库存，清空购物车时会回滚库存，管理员可以通过 \texttt{/admin/restock} 页面登录并进行进货操作。这样，系统不再只是静态展示商品，而是形成了一个较完整的“浏览商品--查询库存--加入购物车--预留库存--清空购物车--释放库存--管理员进货--库存增加”的业务闭环。

\subsection*{原 Online Boutique 系统结构}

Online Boutique 原始系统采用典型的微服务架构。每个服务只负责一类相对独立的业务能力，并通过 gRPC 或 HTTP 等方式进行通信。用户浏览器并不直接访问每一个后端服务，而是统一访问 frontend，由 frontend 根据页面需求再调用其他服务。这样做的好处是前端服务可以作为入口，隐藏内部服务拓扑，降低浏览器端复杂度。

在原有购物流程中，frontend 主要会调用以下服务：

\begin{itemize}
	\item \texttt{productcatalogservice}：提供商品列表、商品详情和商品搜索能力。
	\item \texttt{cartservice}：保存用户购物车内容。
	\item \texttt{currencyservice}：提供货币换算。
	\item \texttt{recommendationservice}：根据当前商品推荐其他商品。
	\item \texttt{adservice}：根据商品类别返回广告内容。
	\item \texttt{checkoutservice}：在结算阶段协调支付、配送和邮件服务。
\end{itemize}

这些服务共同组成了一个可运行的电商网站，但它们没有回答一个关键业务问题：商品到底还有多少库存？例如，用户可以反复把同一件商品加入购物车，系统不会判断库存是否足够；清空购物车也不会恢复库存；管理员也没有单独的补货入口。因此，本次开发没有简单地在商品页面上写死一个库存数字，而是新增独立库存服务，让库存成为系统中的独立业务状态。

\subsection*{新增微服务总体设计}

本次扩展后的系统可以分为两条业务主线：第一条是普通用户购买商品时的库存扣减链路，第二条是管理员补货时的进货链路。

普通用户购买链路如下：

\begin{enumerate}
	\item 用户打开商品详情页。
	\item frontend 调用 productcatalogservice 获取商品基本信息。
	\item frontend 调用 inventoryservice 查询商品库存。
	\item 商品详情页展示剩余库存、库存状态和仓库信息。
	\item 用户选择购买数量，前端根据库存数量限制可选项。
	\item 用户点击加入购物车。
	\item frontend 先调用 inventoryservice 预留库存。
	\item 库存预留成功后，frontend 再调用 cartservice 写入购物车。
	\item 如果写入购物车失败，frontend 调用 inventoryservice 释放刚才预留的库存。
\end{enumerate}

管理员进货链路如下：

\begin{enumerate}
	\item 管理员访问 \texttt{/admin/restock}。
	\item frontend 展示管理员登录页面。
	\item 管理员输入账号和密码。
	\item 登录成功后，frontend 设置管理员会话 Cookie。
	\item 管理员选择商品并填写进货数量。
	\item frontend 携带内部 API Token 调用 restockservice。
	\item restockservice 校验 Token。
	\item restockservice 调用 inventoryservice 增加库存。
	\item 操作成功后，页面弹出进货成功提示，点击确认后刷新页面。
\end{enumerate}

这种设计体现了微服务拆分的基本思想：库存服务只关心库存状态，进货服务只关心进货请求和安全校验，前端只负责用户交互和业务流程编排。三个模块之间通过 HTTP 接口通信，既避免把所有逻辑塞入 frontend，又使新增功能可以被单独测试、单独部署和单独监控。

\subsection*{inventoryservice 库存服务设计与实现}

\subsubsection*{库存数据模型}

库存服务位于 \texttt{src/inventoryservice} 目录中，核心文件为 \texttt{inventory\_service.py}。服务启动时会读取同目录下的 \texttt{inventory.json} 文件，作为初始库存数据。每个商品使用商品 ID 作为键，保存库存数量、库存状态和仓库位置。

库存数据结构示例如下：

\begin{lstlisting}
	{
		"products": {
			"OLJCESPC7Z": {
				"quantity": 18,
				"status": "in_stock",
				"warehouse": "Shanghai-A"
			}
		}
	}
\end{lstlisting}

其中，\texttt{quantity} 表示剩余库存数量，\texttt{status} 表示库存状态，\texttt{warehouse} 表示商品所在仓库。为了让页面展示更直观，库存状态被划分为三类：

\begin{itemize}
	\item \texttt{in\_stock}：库存充足，数量大于 10。
	\item \texttt{low\_stock}：库存较少，数量在 1 到 10 之间。
	\item \texttt{out\_of\_stock}：库存为 0 或更少，表示缺货。
\end{itemize}

库存状态不是由人工长期维护，而是由代码中的 \texttt{status\_for\_quantity} 函数根据库存数量自动计算。这样可以避免出现数量为 0 但状态仍显示为 \texttt{in\_stock} 的不一致情况。

\subsubsection*{库存查询接口}

库存查询接口用于商品详情页展示库存信息：

\begin{lstlisting}
	GET /inventory/{product_id}
\end{lstlisting}

当请求的商品存在时，库存服务返回商品 ID、库存数量、库存状态和仓库位置。例如：

\begin{lstlisting}
	{
		"productId": "OLJCESPC7Z",
		"quantity": 18,
		"status": "in_stock",
		"warehouse": "Shanghai-A"
	}
\end{lstlisting}

如果商品 ID 不存在，则返回 404。这样前端可以区分“商品存在但库存服务暂时不可用”和“库存服务中没有该商品记录”两类情况。

\subsubsection*{库存预留接口}

库存预留接口用于用户加入购物车前扣减库存：

\begin{lstlisting}
	POST /inventory/{product_id}/reserve
	Content-Type: application/json
	
	{"quantity": 2}
\end{lstlisting}

该接口的含义不是最终结算，而是“先把这部分库存锁定给当前购物车”。当库存足够时，服务会执行：

\begin{lstlisting}
	remaining = available - quantity
\end{lstlisting}

并根据剩余数量重新计算库存状态。如果库存不足，例如当前只剩 2 件但用户试图加入 3 件，服务会返回 HTTP 409，表示业务冲突，库存数量不会被修改。

这种设计解决了一个常见问题：如果只在页面上显示库存，而不在服务端扣减库存，用户仍然可能通过重复提交或并发请求购买超出库存的数量。将库存判断放在 inventoryservice 中，可以让库存约束成为服务端规则，而不是单纯依赖前端页面。

\subsubsection*{库存释放接口}

库存释放接口用于把已经预留但不再需要的库存加回去：

\begin{lstlisting}
	POST /inventory/{product_id}/release
	Content-Type: application/json
	
	{"quantity": 2}
\end{lstlisting}

在本系统中，库存释放有两个主要用途。第一个用途是购物车写入失败时进行补偿。例如，frontend 已经成功调用 inventoryservice 扣减库存，但随后调用 cartservice 写入购物车失败。如果不进行补偿，库存就会凭空减少。为了解决这个问题，frontend 会在失败分支调用 release 接口，把刚才预留的库存加回来。

第二个用途是用户清空购物车时回滚库存。用户清空购物车后，购物车中原有商品不再需要占用库存，因此 frontend 会遍历购物车中的每个商品，调用 release 接口恢复库存。

在 restockservice 中，也复用了 release 接口的“增加库存”能力。也就是说，对外表现为管理员进货，内部调用库存服务时使用的是可以增加库存数量的 release 逻辑。这样可以减少库存服务的重复代码，但从接口语义上看，后续如果继续完善系统，也可以在 inventoryservice 中增加专门的 \texttt{/restock} 接口，使“释放预留库存”和“管理员进货”两个动作在命名上更加清晰。

\subsubsection*{并发控制}

库存服务使用 \texttt{threading.Lock} 对库存修改进行保护。原因是库存属于共享状态，如果两个请求同时修改同一个商品库存，就可能出现并发竞争。例如某商品只剩 1 件，如果两个用户几乎同时加入购物车，两个请求都读到库存为 1，然后都扣减成功，就会导致超卖。

因此，在 reserve 和 release 操作中，代码会先进入锁保护区域，再读取和修改库存：

\begin{lstlisting}
	with self.inventory_lock:
	...
\end{lstlisting}

这样同一时刻只有一个请求能够修改库存数据。对于本课程实验中的内存库存实现来说，这种方式简单直接，足以保证单个服务实例内部的库存修改一致性。如果后续扩展到多副本部署或真实生产环境，则应将库存状态迁移到数据库或 Redis 等外部存储，并使用数据库事务或分布式锁保证一致性。

\subsubsection*{健康检查和监控指标}

库存服务提供健康检查接口：

\begin{lstlisting}
	GET /_healthz
\end{lstlisting}

Kubernetes 通过该接口判断服务是否正常运行。服务还提供 Prometheus 格式的监控接口：

\begin{lstlisting}
	GET /metrics
\end{lstlisting}

主要指标包括：

\begin{itemize}
	\item \texttt{inventory\_requests\_total}：按 HTTP 状态码统计库存服务请求次数。
	\item \texttt{inventory\_product\_quantity}：按商品 ID 和库存状态展示当前库存数量。
\end{itemize}

这些指标可以帮助观察系统运行状态。例如，在压测或故障注入时，如果出现大量 409 或 404，就可以从指标中看到异常请求数量；如果某个商品库存持续下降，也可以通过 \texttt{inventory\_product\_quantity} 观察到变化趋势。

\subsection*{restockservice 进货服务设计与实现}

\subsubsection*{服务定位}

进货服务位于 \texttt{src/restockservice} 目录中，核心文件为 \texttt{restock\_service.py}。它的定位不是保存库存，而是提供一个独立的进货后端入口。这样做的原因是：普通用户购买商品和管理员补充库存属于两个不同角色的业务，应该在系统中有清晰边界。

如果把进货逻辑直接写在商品详情页或购物车逻辑中，就会导致购买流程和管理流程混杂在一起。一旦后续增加权限控制、进货记录、供应商管理或审批流程，代码会越来越难维护。因此，本实验将进货能力拆成单独的 restockservice，由 frontend 管理员页面调用它，再由它调用 inventoryservice 更新库存。

\subsubsection*{进货接口}

进货服务提供如下接口：

\begin{lstlisting}
	POST /restock/{product_id}
	Content-Type: application/json
	Authorization: Bearer online-boutique-restock
	
	{"quantity": 5}
\end{lstlisting}

请求体中的 \texttt{quantity} 表示本次进货数量。服务会检查数量是否为正整数，如果数量小于等于 0，则返回 400。服务还会检查请求头中的 \texttt{Authorization} 是否与环境变量中的 \texttt{RESTOCK\_API\_TOKEN} 匹配。如果 Token 不正确，则返回 401。

校验通过后，restockservice 会调用 inventoryservice，将对应商品库存增加。返回结果中包含本次进货数量和更新后的库存信息。例如：

\begin{lstlisting}
	{
		"productId": "66VCHSJNUP",
		"restocked": 5,
		"inventory": {
			"productId": "66VCHSJNUP",
			"quantity": 12,
			"status": "in_stock",
			"warehouse": "Shanghai-A"
		}
	}
\end{lstlisting}

\subsubsection*{为什么需要单独的 API Token}

管理员登录主要保护的是浏览器访问 frontend 的入口，而 API Token 保护的是 frontend 到 restockservice 的服务间调用。二者保护的边界不同：

\begin{itemize}
	\item 管理员账号密码：防止普通用户直接访问管理员进货页面。
	\item \texttt{RESTOCK\_API\_TOKEN}：防止其他内部或外部请求绕过 frontend 直接调用进货服务。
\end{itemize}

因此，系统形成了两层保护。第一层是页面级别的管理员登录，第二层是服务级别的内部令牌校验。虽然本实验中使用的是固定演示 Token，但报告和 README 中已经说明该值只适用于本地课程演示，真实部署时应使用 Kubernetes Secret 或私有配置文件注入。

\subsubsection*{错误处理}

restockservice 在调用 inventoryservice 时设置了 2 秒超时时间。如果库存服务不可用、请求超时或库存服务返回错误，进货服务不会假装成功，而是返回 502，表示后端依赖服务异常。这样前端可以将错误反馈给管理员，同时日志和监控指标中也能看到进货失败的状态。

进货服务同样提供：

\begin{lstlisting}
	GET /_healthz
	GET /metrics
\end{lstlisting}

其中 \texttt{/metrics} 暴露 \texttt{restock\_requests\_total} 指标，用于统计不同状态码的进货请求数量。

\subsection*{frontend 前端改造}

\subsubsection*{商品详情页库存展示}

frontend 的改造主要集中在 Go 代码和 HTML 模板。新增文件 \texttt{inventory\_info.go} 封装了访问库存服务的 HTTP 客户端逻辑。前端启动时从环境变量 \texttt{INVENTORY\_SERVICE\_URL} 读取库存服务地址，在 Kubernetes 中该值配置为：

\begin{lstlisting}
	http://inventoryservice
\end{lstlisting}

当用户打开商品详情页时，frontend 原本只会调用 productcatalogservice 获取商品名称、图片、价格和描述。现在在此基础上又增加了一步：调用 inventoryservice 查询库存信息。查询成功后，页面会展示剩余库存、库存状态和仓库位置。

为了避免用户选择超过库存的购买数量，前端还根据库存数量生成可选数量列表。原系统中数量选项通常是 1、2、3、4、5、10。改造后，如果库存只有 2 件，页面就只显示 1 和 2；如果库存为 0，则按钮会表现为不可购买或提示缺货。这样既改善了用户体验，也减少了无效请求。

\subsubsection*{加入购物车时的库存预留}

原系统中，加入购物车的核心逻辑是 frontend 调用 cartservice，将商品 ID 和数量写入购物车。改造后，该流程被扩展为两阶段：

\begin{enumerate}
	\item frontend 调用 inventoryservice 的 reserve 接口预留库存。
	\item 预留成功后，frontend 调用 cartservice 写入购物车。
\end{enumerate}

这样设计的原因是库存约束应该先于购物车写入。如果库存不足，reserve 接口会返回冲突错误，frontend 就不会继续把商品加入购物车。用户看到的是“库存不足”的错误，而不是购物车里出现一个实际上无法购买的商品。

同时，代码中还处理了补偿逻辑。如果库存预留成功，但写购物车失败，则 frontend 会立即调用 release 接口释放库存。这种处理方式类似分布式系统中的“补偿事务”。虽然它不是严格意义上的数据库事务，但能够保证本实验中库存与购物车之间不会出现明显不一致。

\subsubsection*{清空购物车时的库存回滚}

清空购物车时，frontend 先读取当前购物车内容，保存每个商品 ID 和数量。然后调用 cartservice 清空购物车。清空成功后，再对购物车原有商品逐一调用 inventoryservice 的 release 接口，把之前预留的库存加回去。

这个设计解决了用户反馈的关键问题：购物车清空后，库存应该恢复。否则，用户只是把商品从购物车中删掉，并没有真正购买，库存却减少了，这显然不符合业务逻辑。

\subsection*{Kubernetes 部署与服务发现}

为了让新增微服务能够与原系统一起在 Minikube 中运行，本实验增加了 Kubernetes 部署清单和 Skaffold 构建配置。

在 \texttt{skaffold.yaml} 中，新增了两个构建对象：

\begin{itemize}
	\item \texttt{inventoryservice}，构建上下文为 \texttt{src/inventoryservice}。
	\item \texttt{restockservice}，构建上下文为 \texttt{src/restockservice}。
\end{itemize}

这样执行 \texttt{skaffold run} 时，Skaffold 会自动构建两个新增服务的镜像，并与原系统其他服务一起部署。

在 \texttt{kubernetes-manifests} 目录中新增：

\begin{itemize}
	\item \texttt{inventoryservice.yaml}
	\item \texttt{restockservice.yaml}
\end{itemize}

每个文件中都包含 Deployment、Service 和 ServiceAccount。Deployment 描述 Pod 如何运行，Service 提供稳定的集群内部访问名称，ServiceAccount 则用于符合原项目 Kubernetes 资源组织方式。

frontend 的 Kubernetes 配置中新增环境变量：

\begin{lstlisting}
	INVENTORY_SERVICE_URL=http://inventoryservice
	RESTOCK_SERVICE_URL=http://restockservice
	RESTOCK_API_TOKEN=online-boutique-restock
	ADMIN_USERNAME=admin
	ADMIN_PASSWORD=admin123
	ADMIN_SESSION_TOKEN=online-boutique-admin
\end{lstlisting}

restockservice 的 Kubernetes 配置中新增：

\begin{lstlisting}
	INVENTORY_SERVICE_URL=http://inventoryservice
	RESTOCK_API_TOKEN=online-boutique-restock
\end{lstlisting}

这里的 \texttt{http://inventoryservice} 和 \texttt{http://restockservice} 是 Kubernetes Service 名称。Pod 的 IP 可能变化，但 Service 名称保持稳定，因此服务之间可以通过该名称互相访问。

两个新增服务还都配置了健康检查：

\begin{itemize}
	\item \texttt{readinessProbe}：判断服务是否已经准备好接收请求。
	\item \texttt{livenessProbe}：判断服务是否仍然存活，异常时由 Kubernetes 自动重启。
\end{itemize}

并通过以下注解接入 Prometheus 抓取：

\begin{lstlisting}
	prometheus.io/scrape: "true"
	prometheus.io/path: "/metrics"
	prometheus.io/port: "8080"
\end{lstlisting}

\subsection*{实现过程中的关键问题与解决}

\subsubsection*{问题一：库存显示和库存扣减必须分离}

最初容易想到的做法是在商品详情页直接显示一个库存字段，但这只能解决“看见库存”的问题，不能解决“库存是否真的被占用”的问题。因此最终将库存扣减放在服务端 reserve 接口中，由 inventoryservice 判断库存是否足够。这样即使用户绕过前端页面直接构造请求，也无法购买超过库存的数量。

\subsubsection*{问题二：清空购物车后库存必须回滚}

如果加入购物车时扣减库存，那么清空购物车时就必须释放库存。否则，用户只是取消购买，库存却被永久扣掉。解决方法是在 emptyCartHandler 中先读取购物车内容，清空购物车后再逐项调用 release 接口恢复库存。

\subsubsection*{问题三：购物车写入失败需要补偿}

微服务系统中，一个业务动作往往涉及多个服务。加入购物车就同时涉及 inventoryservice 和 cartservice。如果库存扣减成功但购物车写入失败，就会出现不一致。解决方法是在 frontend 中增加补偿逻辑：只要库存已经预留而购物车写入失败，就调用 release 接口回滚库存。

\subsubsection*{问题四：进货功能不应混入普通购买流程}

管理员进货和普通用户购买属于不同角色的业务。如果将进货按钮放在商品详情页中，会破坏业务边界，也不利于权限控制。因此最终将进货功能放入独立的 \texttt{/admin/restock} 页面，并增加管理员登录逻辑和服务间 API Token。

\subsubsection*{问题五：服务在 Kubernetes 中如何互相访问}

在本地运行程序时，可以使用 \texttt{localhost} 访问服务。但在 Kubernetes 中，每个服务运行在不同 Pod 中，\texttt{localhost} 只表示当前容器自己。因此本实验通过 Kubernetes Service 提供稳定名称，例如 \texttt{inventoryservice} 和 \texttt{restockservice}。frontend 和 restockservice 通过环境变量读取这些地址，从而实现服务发现。

\subsection*{本部分小结}

本部分开发在 Online Boutique 原有微服务系统基础上，新增了 inventoryservice 和 restockservice 两个独立微服务，并对 frontend 进行了业务集成。inventoryservice 将库存从静态页面信息提升为独立业务状态，支持查询、预留、释放、健康检查和监控指标；restockservice 将进货行为从普通购买流程中拆分出来，形成管理员专用模块，并通过账号密码和 API Token 进行双层保护。

通过本次开发，系统形成了较完整的库存业务闭环：商品详情页可以查看库存，加入购物车会预留库存，库存不足会拒绝请求，购物车写入失败会补偿回滚，清空购物车会释放库存，管理员可以登录独立页面进行进货，进货成功后页面弹窗提示并刷新库存。同时，两个新增服务均完成了容器化构建、Kubernetes 部署、健康检查、监控指标暴露和单元测试，符合微服务系统开发的基本要求。
